# 文档同步引擎设计

> 历史同步实现稿：其中专用同步根目录和全量发现规则已被新版按篇关联方案取代。当前产品要求以 [05-product-design.md](./05-product-design.md) 为准。

双向同步，三方比对，乐观锁写入，冲突保留双份。

## 1. 同步单元与映射

只同步 `type = document` 的资产，正文是 markdown。

| asset | Obsidian |
| --- | --- |
| 正文 | `<vault>/<syncRoot>/<path>.md` |
| `path` 字段（服务端新增，见 03 章） | vault 内相对路径 |
| `title` | 文件名（不含扩展名），推送时按路径重新推导 |
| `id`、`lockVersion` | 只存在于本地索引，**不写入文件正文** |

`type = html` 暂不同步。文档中心目前只产出 markdown，为一种尚未出现的资产维护第二套扩展名映射没有收益。

### 1.1 元数据不放 frontmatter

在 frontmatter 里存 `assetId` 很诱人，但有三个问题：

1. **污染内容**——用户在 Web 端会看到 `assetId: doc_xxx` 这类噪音，且 Web 编辑器可能把它当正文改掉
2. **哈希不稳定**——frontmatter 是正文的一部分，注入后本地哈希与服务端的 `content_hash` 永不相等，比对失效
3. **用户可破坏**——手动删掉一行就丢失映射关系

映射关系改为外部索引 `.obsidian/plugins/asset-hub-sync/sync-index.json`：

```ts
interface SyncBinding {
  remoteId:      string;   // doc_xxxxxxxx
  vaultPath:     string;   // 资产中心/产品/周报/W37.md（vault 相对，含扩展名）
  remotePath:    string;   // 产品/周报/W37（服务端 path，不含扩展名）
  baseHash:      string | null;   // 基线：上次同步一致时的内容哈希
  remoteVersion: number;   // 最近一次成功同步时的 lock_version
  updatedAt:     string;   // ISO，服务端 updated_at
  conflicted?:   boolean;  // 已记录冲突，等待用户裁决
  conflictCopy?: string;   // 冲突副本路径
}

interface SyncIndex {
  version:  1;
  bindings: SyncBinding[];
  ignored:  string[];   // 插件自己写出的文件（冲突副本），永不参与上传
}
```

索引按 `vaultPath` 查找（同步扫描天然产出路径），按 `remoteId` 反查用于重命名与删除。这也是重命名能被正确重定基的关键：绑定以路径为键，所以移动文件时必须把整条记录搬过去，而不是只改 `remotePath`（见 §7）。

没有 `workspaceId`：插件连的是当前账号的个人工作空间，令牌决定工作空间，客户端无处选择，因此这层记录是多余的。

`conflictCopy` 同时登记进 `ignored`，但两者职责不同：`conflicted` 让该条目在比对时被跳过，`ignored` 阻止副本文件被当成新文档上传。

### 1.2 哈希算法与服务端一致

服务端 `content_hash` 由 `hashBuffer` 计算（`packages/database/src/storage.ts:33-35`）：

```ts
`sha256:${createHash("sha256").update(data).digest("hex")}`
```

前缀 `sha256:`、hex 小写、无其它编码。输入是 `Buffer.from(text, "utf8")`。

因此插件在**哈希之前**就把 CRLF 规范成 LF，并且**上传的也是规范化后的文本**——否则本地按 LF 算、服务端按收到的 CRLF 算，两端永远算不出同一个值。macOS 上 Obsidian 写出的换行符与 Windows 不一致，这一步不能省。

路径同样要规范化：统一转 NFC。macOS 的文件名是 NFD，Windows/Linux 是 NFC，不统一的话「产品」这个目录会在服务端变成两条不同 `path`。

## 2. 三方比对

每轮同步对每个已绑定文档判定两件事：

| 记号 | 含义 | 来源 |
| --- | --- | --- |
| `L` | 本地当前内容哈希 | 读 vault 文件计算（按 mtime 缓存） |
| `B` | 基线哈希 | 索引 `baseHash` |
| `V` | 远端当前锁定版本 | `GET /assets` 的 `lockVersion` |
| `BV` | 基线版本 | 索引 `remoteVersion` |

| 本地 | 远端 | 结论 | 动作 |
| --- | --- | --- | --- |
| `L == B` | `V == BV` | 都没变 | 跳过 |
| `L != B` | `V == BV` | 仅本地改 | 推送（带 `If-Match: BV`） |
| `L == B` | `V != BV` | 仅远端改 | 拉取覆盖本地 |
| `L != B` | `V != BV` | 双方都改 | 冲突（但见下） |

**远端没有内容哈希**，这是刻意的：算出它意味着每轮下载全部文档。变更检测只依赖索引——即两端上次达成一致的状态——不需要服务端提供任何内容。代价是「远端版本号变了但内容没变」会被判为远端改动，多拉一次；相比每轮全量下载，这个代价可以忽略。

最后一格有个例外。双方都改时先取回远端内容比一次哈希：**若 `L` 等于远端哈希，说明两端改成了同一份内容**（比如都修正了同一个错别字），这不是分歧，直接把基线推进到新版本即可，不生成副本也不提示。这也是「重建索引」能安静收敛的原因——索引清空后，每个两端本来就一致的文档都会走这条路径。

## 3. 冲突处理

冲突时**不覆盖任何一方**。

1. 远端版本写入同目录的副本：`笔记 (冲突 2026-09-10 153045).md`
2. 本地原文件保持不动（用户正在编辑的就是它）
3. 索引中该条目置 `conflicted = true`，记录 `conflictCopy` 与最新的 `remoteVersion`
4. 副本路径登记进 `ignored`，不参与后续同步
5. 通知栏提示，并在侧边栏面板列出

时间戳用本地时间、精确到秒、写成 `YYYY-MM-DD HHMMSS`：`:` 在 Windows 文件名中非法，空格后不带连字符读起来更像「副本」而不是文档名的一部分。

被标记冲突的条目在后续每一轮都被跳过，直到用户裁决——自动选边等于静默丢弃另一份内容。

用户裁决：

- **保留本地** → 以 `remoteVersion` 为 `If-Match` 推送本地内容，删除副本
- **保留云端** → 用副本内容覆盖原文件，基线推进到副本对应的版本，删除副本

两种裁决都删除副本：用户已经做了明确选择，副本正是他要丢弃的那一份。

## 4. 首次推送与并发

```
PATCH /api/v1/assets/:id
If-Match: "<lockVersion>"

{ "title": "W37", "path": "产品/周报/W37", "content": { "kind": "markdown", "text": "..." } }
```

`path` 与 `title` 随每次推送一起带上：本地文件被重命名或移动时，这是让服务端跟上的唯一途径。

响应处理：

- `200` → 用响应里的 `lockVersion` 更新基线
- `409` → 乐观锁竞争。该文档本轮失败并中断整轮（后续动作大概率同样失败），下一轮重新比对时会自然进入冲突或拉取分支
- `401` → 刷新令牌重试**一次**。再失败说明会话真的没了，不再重试
- `403` → scope 不足，提示需重新授权 `documents:write`
- `5xx` / `429` / 网络错误 → 不提示用户（网络抖动自己会好）。整轮失败记入状态栏，单文档失败记入控制台

新建走 `POST /api/v1/assets`，直接带 `path` 与正文。

服务端支持 `Idempotency-Key`，但插件没有用它：重复文档的成因是「请求已落库但响应丢失后重试」，而这里每次推送都由本地扫描驱动，下一轮会通过 `path` 唯一约束（`ASSET_PATH_CONFLICT`）发现重复并报给用户，而不是静默造出第二份。用幂等键需要把键持久化进索引并按文件创建时间派生稳定的键值，这套机制换来的收益在一个由扫描驱动的同步器里不成立。

## 5. 远端扫描

```
GET /api/v1/assets?type=document&limit=100&cursor=<cursor>
```

游标翻完为止。**每轮列举全部文档**，不做 `since` 增量。

服务端支持 `since`（03 章 §2），但增量窗口要求插件自己维护水位线，而删除是以「缺席」表达的——窗口里没有不等于没被删——所以窗口扫描仍要兜底重扫。省下的那点流量抵不过多出来的一条持久化状态和一类边界 bug。文档中心的规模是「一个团队的文档」，全量列举是更便宜的正确性论证。

## 6. 本地变更检测

Obsidian 的 vault 事件不能只依赖——插件未启动时的改动收不到。

**实时**：监听 `modify` / `delete` / `rename`，防抖 3 秒后触发一轮。

**兜底**：启动时、定时（默认 5 分钟）、以及任何手动入口，都跑一次完整扫描。

扫描时按 `mtime` 跳过哈希计算：

```ts
const cached = hashes.get(path);
if (cached && cached.mtime === entry.mtime) continue;   // 未变，复用缓存哈希
hashes.set(path, { mtime: entry.mtime, hash: contentHash(await vault.read(path)) });
```

「mtime 变但内容没变」很常见（编辑后撤销、外部工具触碰文件），所以缓存只用来跳过读取，判断本身永远基于哈希——否则会产生大量空版本。

### 6.1 不做回写抑制

插件写 vault 会触发 `modify` 事件，看起来会形成「拉取 → 触发 → 再拉取」的循环。这里**不做抑制**，因为空转是无害的：事件触发新一轮，扫描发现两端哈希与索引一致，比对结果为空动作，轮次立即结束并写回索引（未变则连索引文件都不写）。

而抑制需要维护一张「这些事件是我自己造的」的时间窗口表，一旦漏掉一次，用户真实编辑就会被当成回显丢掉——一次丢编辑远比多跑几个空轮次严重。另外引擎对自身的写操作会**丢弃**对应的哈希缓存条目，而不是伪造一个 mtime，下一轮读回真实 mtime 后再入缓存。

### 6.2 轮次合并

同步轮次不并发。一轮进行中收到新触发，只置一个「待跑」标记，当前轮结束后再补跑一次——多次触发合并成一次跟进。这比允许并发简单，也避免两轮同时写同一份文件。

## 7. 重命名与移动

Obsidian 的 `rename` 事件同时覆盖改名与移动。

| 场景 | 动作 |
| --- | --- |
| 本地改名 / 移动到别的目录 | `PATCH` 更新 `path` 与 `title`，并把索引绑定搬到新路径 |
| 本地移出 `syncRoot` | 视为「取消同步」：移除绑定，**不删服务端文档** |
| 本地移入 `syncRoot` | 视为新建，`POST /assets` |
| 远端改名 / 移动 | 拉取到新路径，删除本地旧文件与旧绑定 |
| 两端同时改名 | 按远端为准移动本地文件 |

**本地重命名是被「认出来」的，不是被记下来的。** 比对时若某条绑定的本地文件消失，而 `syncRoot` 内出现了一个未绑定、内容哈希恰等于该绑定 `baseHash` 的文件，就判定为移动而非「删除 + 新建」。这避免每次移动都产生一篇新文档。也因此移动的前提是**内容没变**——同时改内容和改名会退化成删除加新建，符合预期。

移动时索引必须整体重定基：绑定以 `vaultPath` 为键，只更新 `remotePath` 会让旧路径的记录悬空，下一轮就会看到「旧文件消失 + 新文件未绑定」，把文档重传成第二份。

「移出 `syncRoot` 不删服务端」是刻意的保守选择：用户拖动文件的意图多是整理，而误删云端文档的代价远高于留一份孤儿数据。

## 8. 删除语义

| 场景 | 动作 |
| --- | --- |
| 本地删除，且开关打开 | `DELETE /assets/:id` 软删，移除绑定 |
| 本地删除，开关关闭（默认） | 仅移除绑定，云端保留 |
| 远端软删，本地未改 | 开关打开则本地文件进 Obsidian 回收站；关闭则只移除绑定 |
| 远端软删，本地有未同步改动 | **不删本地**，移除绑定并提示「云端已删除…已保留本地文件」 |

删除是唯一真正危险的操作，默认**保守**：`本地删除时同步删除云端` 默认关闭。

「本地有未同步改动 + 云端已删」这一格不生成冲突副本：云端那份已经不存在了，没有可保留的另一版。本地文件原样留在 vault 里但脱离同步，用户在面板与通知里会看到原因。

## 9. 无绑定文档

| 场景 | 动作 |
| --- | --- |
| 本地有、远端无 | `POST /assets` 新建 |
| 远端有、本地无 | 拉取落地 |
| 本地有，且某条未绑定远端文档占用了同一路径 | 冲突；取回远端内容比哈希，一致则直接建立绑定（见 §2） |

最后一格是「重建索引」后的常态：索引一空，所有两端都存在的文档都会被视为「未绑定本地 + 占用同路径的未绑定远端」。先比内容再决定，使得重建索引对已同步的 vault 是幂等的——不会为每篇文档造一个冲突副本。

## 10. SSE 实时更新

连接 `GET /api/v1/events`，用 `fetch` + `ReadableStream` 手动解析——Electron 里的 `EventSource` 不能设置请求头，无法传 `Authorization`，而令牌放进查询串会进日志。

- 收到 `asset.*` 事件 → 防抖 2 秒 → 触发一轮完整同步
- 不按 `aggregateId` 做定向拉取：一轮同步本身就是增量的（按哈希与版本判定），定向拉取只是省几次比较，却要为「事件对应的文档该走哪条分支」再维护一套逻辑
- 令牌失效或未登录时直接结束循环，不再重连；下次登录会重新建立
- 其它失败按指数退避重连（1s 起，上限 30 秒）
- SSE 只作**加速**，不作可靠性保证。定时与启动时的完整轮次始终保留

## 11. 调度

```
启动
 ├── 加载索引（损坏则隔离并重建）
 ├── 校验令牌
 ├── 按设置决定是否立即跑一轮（syncOnStartup）
 ├── 启动 vault 事件监听
 ├── 启动定时器（默认 5 分钟）
 └── 建立 SSE 连接

运行中
 ├── vault 事件 → 防抖 3s → 同步轮次
 ├── SSE 事件   → 防抖 2s → 同步轮次
 ├── 定时器     → 同步轮次
 └── 手动入口   → 同步轮次（结束后提示结果）
```

轮次内部**先拉后推**，顺序在引擎里显式排序，而不是依赖比对函数返回的顺序：

```ts
pull: 0, conflict: 1, push-move: 2, push-update: 2, push-create: 3,
delete-local: 4, delete-remote: 4, forget: 5, orphan: 5
```

顺序反了会很糟：本地推送成功会抬高 `lock_version`，随后同一轮里的拉取又用「远端更新」覆盖本地，用户看到自己的编辑被无提示回滚。

**串行执行，不并发。** 一篇文档一个请求，逐条处理。文档中心规模不大，而并发会引入「A 文档失败是否该中断 B 文档」这类需要单独定策略的问题；串行下失败恢复的语义是显然的。

## 12. 错误恢复

| 情形 | 处理 |
| --- | --- |
| 索引 JSON 损坏 | 隔离为 `sync-index.corrupt.json`，按空索引重建。重建后两端一致的文档会被自动认领（§9），不产生副本 |
| 索引版本不认识 | 同上，隔离而不是尝试解析 |
| `syncRoot` 不存在 | 视为暂无本地文件；不报错，用户建好目录后（或拉取时自动创建）即可 |
| 单个文档写失败 | 记入控制台，以 warning 汇总「N 项同步操作失败」，其余文档继续 |
| `path` 冲突（409） | 中断整轮并提示；下一轮比对会把它变成冲突项 |
| 未登录 | 手动同步时提示并打开设置；自动轮次静默跳过 |
| 服务端两个文档 `path` 相同 | 服务端唯一索引阻止其产生；历史数据由迁移去重（03 章 §1.1） |

未处理的边界：`path` 含 Windows 非法字符、超长路径、单文档超过 5MB。三者都需要在**服务端**的路径校验里解决才算真解决——在客户端替换字符会让本地路径与 `remotePath` 不再一一对应，反而破坏映射。当前留待遇到真实数据时处理。

## 13. 可观测性

侧边栏「同步状态」面板：

- 总体状态：同步中 `12/48` / 已同步 / N 个冲突 / 失败
- 最近同步时间与失败原因
- 冲突列表，每条提供「保留本地并覆盖云端 / 保留云端并覆盖本地」
- 手动「立即同步」按钮

状态栏徽标：

```
✓ 已同步 · 3 分钟前
⟳ 同步中 12/48
⚠ 2 个冲突
✕ 同步失败
○ 离线
－ 未登录
```

日志走开发者控制台，由设置项 `输出调试日志` 控制，**不记录文档正文与令牌**。不写 `sync.log` 文件：插件目录里的日志文件既不会被用户看到，又要自己实现滚动与清理，而 Obsidian 的开发者控制台已经提供了同等的可获取性。

## 14. 验证要点

不依赖 Obsidian 实例的部分全部单测（见 04 章 §13）：

- 比对矩阵：空闲、仅本地改、仅远端改、双方改、内容巧合一致
- 重命名识别为移动，且移动后一轮不再重传
- 本地删除在开关开 / 关下的两种结果
- 远端删除在本地未改 / 已改下的三种结果
- 路径冲突与「内容一致则认领」
- 内容哈希与 CRLF 规范化、NFC 路径规范化
- 索引读写、损坏隔离、`settle` 清理冲突标记
- 冲突副本的创建、裁决与副本删除
- 令牌单飞刷新（并发只刷一次）
- SSE 帧解析
- 轮次合并、先拉后推顺序、进度与完成时间
